# 後端常用
## Express

### 核心功能

- **輕量級 Web 框架**：提供極簡的架構，專門用來建立 Web 應用程式與 RESTful API。
- **中間件 (Middleware) 機制**：核心設計模式。請求 (Request) 進入到回應 (Response) 結束之間，可以串聯多個中間件來處理身份驗證、日誌記錄、資料解析等。
- **強大的路由 (Routing)**：透過簡單的 `app.get()`, `app.post()` 等方法，輕鬆定義 URL 路徑與 HTTP 動態行為。

### TypeScript 支援度

- **支援度：社群支援 (`@types/express`)**
- **說明**：Express 本身是用純 JavaScript 寫的，源碼內沒有型別定義。在 TS 專案中使用時，你**必須**額外安裝社群維護的型別庫：

``` bash
npm install express
npm install -D @types/express
```


- **開發體驗**：安裝 `@types` 後，TS 支援度非常好。你可以直接匯入 `Request`, `Response`, `NextFunction` 等型別來規範你的路由與中間件函數，享有完整的代碼補全 (IntelliSense)。

> **筆記核心提醒：**
> 雖然 Express 加上 `@types` 很好用，但因為它本質上是純 JS 框架，對於非同步錯誤 (Async Errors) 的型別捕捉在舊版本較不直覺（通常需要手動 `next(err)` 或使用 `express-async-errors` 套件）。

## Helmet

### 核心功能

- **HTTP 標頭安全防護**：Helmet 是一個 Express 的中間件集合，透過設定各種安全性相關的 HTTP 回應標頭 (Response Headers)，來保護你的應用程式免於一些常見 Web 漏洞的攻擊。
- **主要防護機制包括**：
    - **隱藏敏感資訊**：例如移除 `X-Powered-By` 標頭，不讓黑客輕易知道你後端是用 Express 寫的。
    - **防止點擊劫持 (Clickjacking)**：設定 `X-Frame-Options`，防止你的網站被惡意嵌入到別人的 `<iframe>` 中。
    - **內容安全政策 (CSP, Content Security Policy)**：設定 `Content-Security-Policy` 標頭，嚴格限制瀏覽器只能載入信任來源的腳本或資源，大幅降低 XSS (跨網站指令碼) 攻擊的風險。
    - **強制 HTTPS**：設定 `Strict-Transport-Security` (HSTS)，告訴瀏覽器未來只能透過安全的 HTTPS 訪問該網站。

### TypeScript 支援度

- **支援度：內建支援 (Built-in)**
- **說明**：Helmet 從大版本 `v4` 開始，官方就已經**直接將 TypeScript 型別定義內建在套件中**了。因此你完全不需要額外安裝 `@types/helmet`，直接安裝主套件即可：

```bash
npm install helmet
```

- **開發體驗**：開箱即用！在 TS 中匯入時非常直覺。當你需要調整 Helmet 的複雜設定（例如自訂 CSP 的白名單規則）時，TS 的自動補全與型別檢查能完美幫你避開拼錯單字的低級錯誤。


```ts
import express from 'express';
import helmet from 'helmet';

const app = express();

// 享有完整的型別提示與自動補全
app.use(helmet({
	contentSecurityPolicy: {
      directives: {
        defaultSrc: ["'self'"],
        scriptSrc: ["'self'", "trusted-cdn.com"]
      }
    }
}));
```

> **筆記核心提醒：**
> 如果你在安裝舊專案或參考舊版教學時看到有人寫 `npm install @types/helmet`，那是過去式的做法（現在的 `@types/helmet` 只是一個空殼）。直接裝 `helmet` 本身就可以了。另外，因為它本質上是修改 Headers，通常會建議將它**放在所有路由與中間件的最上方**優先執行。

## Jsonwebtoken

### 核心功能

- **生成與驗證 JWT**：專門用來實作基於 Token 的身分驗證機制。
- **主要 API 只有三個，非常直覺**：
    - `jwt.sign()`：將使用者資訊（Payload）加上密鑰（Secret/Private Key）進行數位簽章，**生成一串加密字串 (Token)**。通常可以設定過期時間（如 `expiresIn: '1h'`）。
    - `jwt.verify()`：接收前端傳回的 Token，並用密鑰進行**驗證與解碼**。如果 Token 被竄改、過期或密鑰錯誤，會直接拋出錯誤。
    - `jwt.decode()`：純粹**解碼** Token 內容，**不進行簽章驗證**（通常用於前端只想讀取 Payload 資訊，後端安全檢查千萬不能只用這個）。

### TypeScript 支援度

- **支援度：社群支援 (`@types/jsonwebtoken`)**
- **說明**：這個套件本身是用純 JavaScript 寫的，所以跟 Express 一樣，在 TS 專案中必須安裝社群維護的型別宣告檔案：

```bash
npm install jsonwebtoken
npm install -D @types/jsonwebtoken
```

- **開發體驗**：中上。基本語法（如參數、設定項）的提示很完整，但有一個在 TS 開發時**極度容易踩坑**的地方：

> ⚠️ **TS 開發痛點：解碼後的 Payload 型別**
> 當你使用 `jwt.verify()` 成功解碼後，TS 預設給它的回傳型別是 `string | JwtPayload`。
> 因為 TS 不知道你當初在 Payload 裡塞了什麼欄位（例如 `userId`, `role`），如果你直接讀取 `payload.userId`，TS 會報錯說 `Property 'userId' does not exist on type 'string | JwtPayload'`。

#### 💡 TS 筆記實戰解法：

在 TS 中，你通常需要使用**型別斷言 (Type Assertion)** 來告訴 TS 這串資料的真實結構：

```ts
import jwt from 'jsonwebtoken';

// 1. 定義你專案專屬的 Payload 介面
interface MyTokenPayload extends jwt.JwtPayload {
  userId: string;
  role: string;
}

const token = '...';
const secret = 'your-secret-key';

try {
  // 2. 使用 as 斷言正確的型別
  const decoded = jwt.verify(token, secret) as MyTokenPayload;
  
  // 現在你可以安全且享有補全地使用自訂欄位了！
  console.log(decoded.userId); 
  console.log(decoded.role);
} catch (error) {
  // 處理 Token 過期或無效
}
```

> **筆記核心提醒：**
> JWT 的 Payload 內容只是被「編碼（Base64）」，**並沒有被加密**。任何拿到 Token 的人都可以輕易解碼看到裡面的內容。因此，**千萬不要把敏感資訊（例如密碼、信用卡號）塞進 JWT 的 Payload 裡**！它只適合放非敏感的識別資料（如 `userId`）。

## Cors

### 核心功能

- **解決瀏覽器同源政策 (Same-Origin Policy) 的限制**：當你的前端（例如 `http://localhost:3000`）去呼叫不同網域的後端（例如 `http://localhost:5000`）時，瀏覽器預設會基於安全理由阻擋回應。這個套件就是用來幫後端自動設定正確的 `Access-Control-Allow-Origin` 等 HTTP 標頭。
- **快捷設定中間件**：
    - **全開模式**：一鍵允許所有網域的跨域請求（適用於公開 API）。
    - **限制模式**：精準限制只有特定的白名單網域、特定的 HTTP 方法（GET/POST 等）、或是否允許攜帶 Cookie (Credentials)。

### TypeScript 支援度

- **支援度：社群支援 (`@types/cors`)**
- **說明**：`cors` 是一個歷史悠久的純 JavaScript 套件，官方源碼不包含型別定義。在 TS 專案中，你**必須**額外安裝社群維護的型別庫：

```bash
npm install cors
npm install -D @types/cors
```

- **開發體驗**：非常棒！安裝 `@types/cors` 後，當你需要設定複雜的跨域規則時，TS 會提供完整的配置項提示（`CorsOptions`），完全不用死記各個設定的名稱。

```ts
import express from 'express';
import cors from 'cors';

const app = express();

// 精準設定的範例，享有完整的 TS 自動補全與型別檢查
const corsOptions: cors.CorsOptions = {
  origin: ['https://www.your-production-site.com', 'http://localhost:3000'],
  methods: 'GET,HEAD,PUT,PATCH,POST,DELETE',
  credentials: true, // 允許前端攜帶 Cookie 或認證標頭
  optionsSuccessStatus: 200 // 針對一些舊版瀏覽器 (如 IE11) 的 204 回應問題
};

app.use(cors(corsOptions));
```

> **筆記核心提醒：**
> 如果直接寫 `app.use(cors())` 不帶任何參數，預設會是 **「全開模式」**（允許所有來源 `*`）。在開發階段很方便，但**部署到生產環境 (Production) 時，務必改成白名單限制**，否則等同於對全網路敞開大門，會帶來安全隱患。

## Bcryptjs

### 核心功能

- **密碼安全雜湊（Password Hashing）**：專門用來處理使用者密碼的加密儲存。它採用了嚴格的 **Blowfish 密碼演算法**，最大的特點是「慢」，這能有效抵禦暴力破解法（Brute Force）與彩虹表（Rainbow Table）攻擊。
- **自動加鹽（Salting）**：在雜湊過程中，會自動隨機生成一串稱為「鹽（Salt）」的隨機字串並混入密碼中。這意味著**即使兩個使用者的原始密碼完全相同，加密後的字串也會完全不同**。
- **核心 API 只有兩個對抗組**：
    - **非同步（推薦）**：`bcrypt.hash()`（加密）與 `bcrypt.compare()`（驗證）。
    - **同步（不推薦，會阻塞 Node.js 事件循環）**：`bcrypt.hashSync()` 與 `bcrypt.compareSync()`。

### TypeScript 支援度

- **支援度：社群支援 (`@types/bcryptjs`)**
- **說明**：`bcryptjs` 本身是純 JavaScript 寫成的套件，需要搭配社群提供的型別宣告檔案：

```bash
npm install bcryptjs
npm install -D @types/bcryptjs
```

- **開發體驗**：非常單純直接。主要的型別通常只涉及 `string`、`number`（控制加密複雜度的 rounds），因此在 TS 中幾乎不會遇到需要複雜型別處理的痛點。

```ts
import bcrypt from 'bcryptjs';

const myPlainPassword = 'superSecretPassword123';
const saltRounds = 10; // 複雜度，通常 10 ~ 12 是目前效能與安全的平衡點

// 1. 註冊時：將密碼雜湊化後再存入資料庫
async function registerUser(password: string) {
  const hashedPassword = await bcrypt.hash(password, saltRounds);
  // 存入資料庫：hashedPassword (通常是一串以 $2a$ 開頭的 60 字元字串)
}

// 2. 登入時：比對明文密碼與資料庫中的雜湊密碼
async function loginUser(passwordInput: string, storedHash: string) {
  // 注意：不能用 === 直接比對！必須用 bcrypt.compare
  const isMatch = await bcrypt.compare(passwordInput, storedHash);
  
  if (isMatch) {
    console.log('登入成功！');
  } else {
    console.log('密碼錯誤！');
  }
}
```

> **💡 補充一個容易搞混的面試級冷知識（bcrypt vs bcryptjs）：**
> 
> - **`bcrypt`**：底層是用 **C++** 寫的，效能極高，但安裝時需要依賴作業系統的編譯環境（node-gyp），在不同的作業系統（例如 Windows 換到 Linux 容器）常常會遇到安裝失敗的噩夢。
> - **`bcryptjs`**：底層是用 **純 JavaScript** 重新實作的。雖然執行速度比 C++ 版慢了一點點，但**完全不需要編譯環境，在任何平台都能一鍵安裝成功**。對於高併發的後端服務來說，那一點點速度差距在安全性保護前通常可以忽略，因此 `bcryptjs` 成了 Node.js 社群最受歡迎的選擇。

## Cookie-parser

### 核心功能

- **解析 Cookie 標頭**：瀏覽器每次發送請求時，會自動把該網域的 Cookie 放在 HTTP 請求標頭的 `Cookie` 欄位中（格式是一長串字串，如 `name=alex; age=20`）。這個套件會自動將它解析成一個乾淨的 **JavaScript 物件**，並掛載在 `req.cookies` 上。
- **支援簽章 Cookie (Signed Cookies)**：這是它最重要的安全功能。你可以傳入一個「祕鑰 (Secret)」。當你產生 Cookie 時對它進行數位簽章，當瀏覽器傳回來時，`cookie-parser` 會驗證該 Cookie 是否被前端或第三方竄改過。如果沒被竄改，會解密並掛載在 `req.signedCookies` 上；如果被動過，則會變成 `false`。

### TypeScript 支援度

- **支援度：社群支援 (`@types/cookie-parser`)**
- **說明**：這個套件也是經典的純 JS 庫，需要搭配社群提供的型別宣告檔案：

```bash
npm install cookie-parser
npm install -D @types/cookie-parser
```

- **開發體驗**：配合 Express 使用時體驗很好。安裝型別檔後，Express 的 `Request` 物件會自動被擴充，讓你存取 `req.cookies` 和 `req.signedCookies` 時擁有正確的型別提示。

```ts
import express from 'express';
import cookieParser from 'cookie-parser';

const app = express();

// 傳入一個祕鑰用來啟用簽章功能
app.use(cookieParser('my-super-secret-key'));

app.get('/read-cookie', (req, res) => {
  // 1. 讀取一般 Cookie
  const theme = req.cookies.theme; 
  
  // 2. 讀取簽章（安全）Cookie
  // 如果前端自己去 DevTools 修改了這個值，這裡會拿不到，以此確保資料真實性
  const userId = req.signedCookies.userId; 

  res.send(`主題: ${theme}, 用戶ID: ${userId}`);
});

app.get('/set-cookie', (req, res) => {
  // 設定一個帶有簽章的 Cookie，過期時間 1 天
  res.cookie('userId', '12345', { 
    signed: true, 
    httpOnly: true, // 防止前端 JS 透過 document.cookie 讀取（防 XSS）
    maxAge: 86400000 
  });
  res.send('Cookie 已設定');
});
```

> **筆記核心提醒：**
> 
> 1. 簽章 Cookie (`signed: true`) **並不等於加密**！使用者在瀏覽器裡依然看得到這條 Cookie 的文字，只是後面多了一串簽章後綴（例如 `s:12345.xxxxxx`）。它防的是「竄改」，不防「偷看」。所以絕對不要把敏感資料（如密碼）明文存在 Cookie 裡。
> 2. 為了安全，設定重要 Cookie 時務必加上 `{ httpOnly: true, secure: true }` 選項。

接下來是無論在前端還是後端，用來產生「全球唯一識別碼」出鏡率 100% 的基礎套件 —— **uuid**。

## uuid

### 核心功能

- **生成唯一識別碼 (UUID/GUID)**：產生一串由 36 個字元組成的隨機字串（包含 32 個十六進位字元與 4 個連字號，例如 `1b9d6bcd-bbfd-4b2d-9b5d-ab0df50e4334`）。
- **實務上最常用的版本**：
    - **v4 (基於隨機數)**：完全隨機產生。碰撞機率微乎其微（低到可以忽略不計），這也是**日常開發中最常拿來當作資料庫 Primary Key、訂單編號或檔案名稱的版本**。
    - **v1 (基於時間戳記)**：結合了電腦的 MAC 位址與目前的時間。雖然能保證唯一性，但因為包含了 MAC 位址，在注重隱私與安全的場景較少使用。
    - **v7 (結合時間與隨機，較新)**：在較新的開發環境中很受歡迎，因為它把時間戳記放在最前面，生成的 UUID 具備「時序性（可以按時間排序）」，這對資料庫索引（Index）的效能非常友善。

### TypeScript 支援度

- **支援度：社群支援 (`@types/uuid`)**
- **說明**：`uuid` 套件官方源碼仍為純 JS，在 TS 專案中，你**必須**額外安裝社群維護的型別庫：

```bash
npm install uuid
npm install -D @types/uuid
```

- **開發體驗**：非常棒！因為它的 API 極度簡單，基本上只有導出各版本的函數，因此搭配 `@types` 後，使用上完全不會遇到型別卡關的問題。

```ts
// 實務上最常見的寫法：將 v4 重新命名為 uuidv4 以便閱讀
import { v4 as uuidv4, v7 as uuidv7 } from 'uuid';

// 1. 生成一個標準的 v4 隨機 UUID
const userId: string = uuidv4(); 
console.log(userId); // 輸出例如: "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d"

// 2. 生成一個具備時序性的 v7 UUID (適合需要排序的資料庫主鍵)
const orderId: string = uuidv7();
console.log(orderId);
```

> **筆記核心提醒：**
> 
> 1. `uuid` 本身生成的結果就是一個單純的 `string` 型別。
> 2. **面試或架構設計小知識**：如果你的專案正在使用 **MySQL** 這類使用 B-Tree 索引的關聯式資料庫，傳統的 **v4 UUID 由於完全隨機，會導致嚴重的磁碟隨機寫入問題（索引碎片化）**。在這種場景下，建議優先考慮使用 **v7**，或者在資料庫底層由 MySQL/PostgreSQL 內建的函數來生成 UUID。
